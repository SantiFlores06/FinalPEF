¿Qué resuelve?

Objetivo del
proyecto

El usuario elige varias ciudades europeas, un medio de transporte y si quiere minimizar costo o tiempo de viaje. El sistema calcula dos rutas: la que el usuario armó en el orden elegido, y la ruta óptima calculada automáticamente mediante TSP.

Ambas rutas se muestran comparadas con sus costos totales, para que el usuario pueda tomar una decisión informada. Luego puede crear una reserva que pasa por un flujo asincrónico de confirmación con estados visibles en tiempo real.

Criterios de optimización

El usuario puede elegir entre minimizar el costo total o minimizar el tiempo de traslado. Esto cambia el peso de las aristas del grafo antes de correr los algoritmos, dando resultados diferentes para el mismo conjunto de ciudades.

Validador de itinerarios

itinerary_validator.py aplica reglas sobre el itinerario generado: presupuesto máximo, duración máxima, cantidad de segmentos, ciudades requeridas o prohibidas, tipos de transporte permitidos y consistencia de horarios.

Explicación inicial · ruta simple vs multidestino

Cómo trabaja
el optimizador

El sistema no usa un único algoritmo para todo. Separa el problema en dos niveles: primero calcula caminos mínimos entre puntos y después optimiza el orden completo de visita cuando hay varias ciudades.

Para una ruta puntual, por ejemplo Madrid → Roma, se usa Dijkstra. Para un recorrido con varias ciudades, por ejemplo Madrid → París → Roma → Berlín, se usa TSP para encontrar el mejor orden posible.

Flujo algorítmico
Ciudades seleccionadas
→
Matriz costo/tiempo
→
TSP
→
Ruta óptima

“Dijkstra me responde cuál es el mejor camino entre dos ciudades. TSP me responde en qué orden conviene visitar muchas ciudades. Por eso se complementan dentro del planificador.”

Dijkstra

1 origen → 1 destino

Se aplica sobre el grafo de ciudades. Cada conexión tiene costo, tiempo y transporte. El algoritmo encuentra el camino mínimo usando una cola de prioridad.

TSP / Held-Karp

1 origen → N ciudades

Se usa cuando el usuario selecciona múltiples destinos. Evalúa combinaciones con programación dinámica, bitmasking y memoización para minimizar costo o tiempo total.

Aclaración importante

En este proyecto ambos algoritmos están integrados en la API, pero para el TSP la matriz se arma desde los datos generados en routes_fixed.py, no desde una ejecución all-pairs de Dijkstra.

app/core/

Algoritmos de
optimización

Dijkstra — Camino mínimo

graph.py

Implementado sobre un grafo dirigido de ciudades. Cada arista tiene peso de costo y de tiempo, más una etiqueta de tipo de transporte. Antes de ejecutar la búsqueda se puede filtrar por transporte, descartando aristas que no corresponden.

Usa una min-heap (cola de prioridad) para explorar siempre el nodo con menor costo acumulado primero. Se detiene al alcanzar el destino.

class Route: destino: str costo: float tiempo: float transporte: str # auto | tren | avion # Llamada al algoritmo grafo.dijkstra( origen="Madrid", destino="Roma", criterio="costo", transporte="tren" )

Complejidad temporal

O((V + E) log V) con min-heap, donde V = ciudades, E = rutas. Eficiente para el grafo europeo que maneja el sistema.

TSP Held-Karp (DP + bitmask)

tsp_dp.py

Resuelve el Problema del Viajante para múltiples destinos. Usa programación dinámica con bitmask para representar el subconjunto de ciudades visitadas, y memoización para evitar recalcular estados ya computados.

El estado del DP es dp[mask][i] = costo mínimo de llegar a la ciudad i habiendo visitado exactamente las ciudades indicadas en el bitmask. Al final reconstruye el camino recorriendo las decisiones almacenadas.

# Estado del DP dp[mask][i] = costo_min_para_llegar a ciudad[i] habiendo visitado ciudades en {mask} # Transición for j en ciudades no visitadas: dp[mask | (1<<j)][j] = min(dp[mask][i] + dist[i][j]) # Complejidad Tiempo: O(n² · 2ⁿ) Espacio: O(n · 2ⁿ)

Tour cerrado vs abierto

El solver soporta ambas variantes: con regreso al origen (tour cerrado, el clásico TSP) y sin regreso (tour abierto), según lo que necesite el itinerario del usuario.

05 / 14
Justificación de la elección

¿Por qué
Algoritmo Genético?

Para reemplazar a Held-Karp en 13+ ciudades había varias familias de heurísticos posibles. La decisión no fue "cualquier heurístico sirve" — se comparó contra las alternativas más directas antes de elegir cuál implementar.

Alternativas consideradas

Nearest Neighbor greedy · O(n²)

Construye una única solución y nunca la mejora. Rápido, pero la calidad depende del punto de partida y no hay margen de ajuste.

2-Opt mejora local · O(n²)/iter

Mejora un tour existente intercambiando aristas, pero queda atrapado en óptimos locales sin forma de escapar.

Recocido Simulado metaheurístico · O(iter)

Explora una sola solución a la vez, aceptando empeoras controladas. No aprovecha diversidad poblacional.

“Un heurístico poblacional no busca una única respuesta — mantiene muchas en simultáneo y deja que compitan. Eso es lo que hace al Genético distinto de un greedy o de una mejora local.”

Por qué se eligió el Genético

Poblacional, no de una sola solución

Evoluciona 150–200 individuos en paralelo por generación; el cruce (OX) combina buenas subrutas de padres distintos en vez de partir de una sola.

Nunca pierde lo mejor encontrado

El elitismo pasa los 2 mejores individuos intactos a la siguiente generación — a diferencia de 2-Opt o Recocido Simulado, no hay riesgo de retroceder.

Extensible sin tocar el algoritmo

El fitness (1/costo) podría sumar restricciones reales — presupuesto, tiempo, ciudades prohibidas — sin cambiar selección, cruce ni mutación.

Demostrable en vivo

La evolución generación a generación es visual y medible: history guarda best_cost y avg_cost por generación, graficado en la UI con barra de progreso en tiempo real.

Trade-off asumido

A cambio de esa flexibilidad y escalabilidad, el Genético no garantiza el óptimo. El Laboratorio existe justamente para medir ese costo: el gap de optimalidad frente a Held-Karp.

app/core/tsp_genetic.py · clase GeneticTSP

Algoritmo Genético —
TSP heurístico

Held-Karp es exacto pero explota exponencialmente: con 20 ciudades son 20² × 2²⁰ ≈ 419 millones de estados, inviable en una UI web. El genético resuelve el mismo problema con complejidad O(generaciones × población × n), totalmente controlable.

Lógica de umbral (routing)
2 ciudades → Dijkstra
·
3–12 → Held-Karp
·
13–25 → Genético

Codificación (cromosoma)

Permutación de índices de ciudades. [0, 3, 1, 2] = Madrid → Viena → Barcelona → Roma → (Madrid). Fitness = 1 / costo total del tour.

Constante de corte

MAX_HELD_KARP = 12. Con n=12 son ~590K operaciones (~500ms); con n=20, ~419M — el corte evita que la UI se congele.

Operadores evolutivos

Selección — Torneo

5 candidatos al azar, gana el de menor costo.

Cruce — Order Crossover (OX)

Toma un segmento del padre 1 y rellena con el orden del padre 2, sin repetir ciudades. La ciudad inicial queda siempre fija.

Mutación — Swap

Intercambia dos ciudades al azar. Probabilidad 2%.

Elitismo

Los 2 mejores individuos pasan directo a la próxima generación — la mejor solución nunca se pierde.

# Order Crossover (OX) parent1: [0, 1, 2, 3, 4] parent2: [0, 3, 1, 4, 2] segmento [1:3] de parent1 → [1, 2] hijo: [0, 3, 1, 2, 4] # relleno de parent2 # Parámetros (13+ ciudades, solver principal) population_size = 200 generations = 400 mutation_rate = 0.02 elitism = 2

# Extrapolación calibrada con el último punto medido C = hk_ms_medido / (n² · 2ⁿ) for k in range(n_medido, 18): proyectado[k] = C * k**2 * 2**k # Cruce: primer k donde el exacto proyectado # supera al promedio del genético

Hallazgo pedagógico

El genético tiene un costo fijo alto (población × generaciones): para pocas ciudades Held-Karp es más rápido además de exacto. La ventaja del heurístico no es la velocidad con n chico — es que sigue siendo viable cuando el exacto ya no puede correr.

Dijkstra — graph.py

TravelGraph

La clase TravelGraph representa las ciudades como nodos y las rutas como aristas ponderadas.

def dijkstra(source, target, weight, transport_type): priority_queue = [(0, source)] while priority_queue: current_distance, current_node = heapq.heappop(priority_queue) for route in graph[current_node]: edge_weight = getattr(route, weight) new_distance = current_distance + edge_weight

“cada vez que encuentra una ruta mejor, actualiza la distancia y el predecesor para reconstruir el camino final.”

Endpoints relacionados

/routes/shortest calcula un camino mínimo. /routes/compare compara la ruta del usuario contra una ruta optimizada usando Dijkstra con filtro de transporte.

TSP — tsp_dp.py

TSPSolver

La clase TSPSolver implementa Held-Karp. Usa un bitmask para saber qué ciudades ya fueron visitadas.

if mask == (1 << n) - 1: return cost[pos][start] # tour cerrado for next_city in range(n): if mask & (1 << next_city): continue new_mask = mask | (1 << next_city) best = min(best, cost[pos][next_city] + tsp(new_mask, next_city))

En la defensa: “no elige simplemente la ciudad más cercana; evalúa subproblemas y guarda el mejor resultado global.”

Endpoint relacionado

/routes/optimize-multi recibe la matriz y las ciudades seleccionadas, ejecuta TSPSolver.solve() y devuelve la ruta óptima.

¿De dónde vienen los datos?

routes_fixed.py genera automáticamente rutas entre ciudades europeas a partir de coordenadas geográficas reales. Usa la fórmula de Haversine para calcular la distancia real sobre la esfera terrestre entre cada par de ciudades.

def haversine(lat1, lon1, lat2, lon2): R = 6371 # radio Tierra en km dlat = radians(lat2 - lat1) dlon = radians(lon2 - lon1) a = sin(dlat/2)**2 + cos(lat1) \ * cos(lat2) * sin(dlon/2)**2 return R * 2 * asin(sqrt(a)) # Genera costo y tiempo por transporte costo_avion = distancia * FACTOR_AVION tiempo_tren = distancia / VELOCIDAD_TREN

A partir de la distancia se derivan el costo estimado y el tiempo de viaje para cada tipo de transporte, generando una red coherente sin depender de APIs externas.

Estructura del grafo
Nodos (ciudades) Madrid, París, Roma…
Aristas (rutas) dirigidas, con peso doble
Peso por arista costo · tiempo · transporte
Filtro pre-algoritmo por tipo de transporte

Matriz de costos para TSP

Los mismos datos alimentan la matriz n×n requerida por Held-Karp. El endpoint /routes/matrix la expone para que la UI la solicite.

Sin dependencias externas

Todo el sistema de datos funciona offline. No depende de APIs de mapas ni servicios de terceros para generar las rutas base.

¿Por qué async?

Las reservas simulan operaciones reales con proveedores externos: confirmación, validaciones, notificaciones. Estas operaciones pueden tardar varios segundos. Con asyncio el servidor no se bloquea mientras espera — sigue atendiendo otras peticiones en paralelo.

Procesamiento batch

batching.py agrupa múltiples reservas y las procesa juntas en un lote. Ideal para simular carga masiva sin saturar la respuesta inmediata del servidor. El loop corre en background y drena la cola de a tandas.

app/caches/

Estrategia de
caché

LRU Cache local

lru_cache.py

Implementado desde cero sin librerías externas. Mantiene los resultados de cálculos recientes en memoria. Cuando supera la capacidad configurada, descarta el elemento menos recientemente usado (Least Recently Used).

Incluye una variante con TTL (Time To Live): las entradas expiran automáticamente tras un tiempo configurado, evitando que datos desactualizados persistan en caché indefinidamente.

También se provee un decorador @lru_cache para aplicar caché fácilmente a cualquier función del sistema.

# Uso como decorador @lru_cache(capacity=128, ttl=300) def calcular_ruta(origen, destino, criterio, transporte): # cálculo costoso sólo la 1ra vez return dijkstra(origen, destino)

Redis Cache (distribuido)

redis_cache.py

Alternativa implementada para escenarios donde múltiples instancias de la API comparten el mismo caché. Requiere un servidor Redis corriendo externamente.

La lógica de la aplicación es idéntica en ambos casos: el módulo de caché es intercambiable. Se activa Redis simplemente cambiando la configuración, sin tocar los algoritmos ni los endpoints.

¿Qué se cachea?

✓ Resultados de Dijkstra por par origen–destino
✓ Optimizaciones TSP por conjunto de ciudades
✓ Matrices de costos por tipo de transporte
